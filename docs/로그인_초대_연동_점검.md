## 재현 테스트

가상 기기 테스트 3개를 실행했다. 1개 통과, 2개 실패, 오류/건너뜀 없음.

- `blankCredentialsMustNotEnterHome`: 빈 입력으로 로그인 클릭 후 홈에 진입하여 실패.
- `invalidCredentialsMustNotEnterHome`: 존재하지 않는 테스트 입력으로 로그인 클릭 후 홈에 진입하여 실패. 실제 자격 증명을 입력하지 않았다.
- `FirebaseLiveIntegrationTest.isolatedLiveRoundTrip`: 통과. 기존 서버 기능 검증에 초대 조회/자가 등록 차단 확인을 추가했다.

로그인 로그는 두 경우 모두 `identityChanged=false authenticatedAfter=false`다. 즉 인증된 Firebase 사용자가 만들어지지 않았는데 홈으로 이동했다.

실서버에서 임시 여행에 고유한 검증용 inviteCode를 넣은 뒤, 비멤버 계정으로 기존 조회 형태(`whereEqualTo("inviteCode", ...).limit(1)`)를 실행했다. 서버가 PERMISSION_DENIED로 거부했다. 비멤버의 직접 members 등록도 거부했다.

```text
INVITE_AUDIT legacyQueryDenied=true uninvitedSelfAddDenied=true
SERVER_ACCESS removedMemberReadDenied=true removedMemberWriteDenied=true removedMemberReaddDenied=true
RESULT stage=complete failure=null cleanupErrors=[]
```

이 거부는 기존 서버 접근 차단이 정상이라는 뜻이다. 초대를 작동시키려고 trips 전체 조회나 members 자기 등록을 다시 공개하면 안 된다. 초대용 권한 흐름을 따로 구현해야 한다.

검증용 인수 테스트는 실제 인증 요구사항을 검사하므로 현재 실패 상태를 유지한다. 일반 실행은 `mbtripLoginAudit=true` 없이는 이 인수 테스트를 건너뛴다. 기존 화면 이동 smoke test의 통과는 실제 로그인 성공을 의미하지 않는다.

## 다음 구현 순서

1. 이메일/비밀번호 인증 제공자 설정과 실제 가입·로그인을 연결한다. 현재 UI는 이메일 또는 아이디 입력을 받지만 Firebase 이메일 인증만 연결한다면 입력 안내도 일치시켜야 한다. 아이디 로그인을 유지하려면 별도의 안전한 아이디→계정 해석 방식이 필요하다.
2. 기존 익명 UID로 저장한 진단·여행을 잃지 않도록 신규 계정 가입 시 익명 계정 연결 방식을 검토한다. 이미 존재하는 계정으로의 로그인과 계정 간 데이터 이관은 별도 처리한다. 검증 없이 기존 방의 ownerId를 다른 UID로 바꾸지 않는다.
3. Auth 상태 변경 시 이전 여행/멤버 구독을 초기화하고 로그인 UID의 프로필·진단 점수를 서버에서 읽는다. 현재 cachedScore는 기기 로컬 값만 읽으므로 다른 기기 로그인 후 프로필 복원이 필요하다.
4. 초대 발급·만료/취소·참여 승인 흐름과 서버 검사를 함께 설계한다. 생성자가 사용자 UID를 초대/승인하는 기존 권한 모델 또는 별도 초대 토큰/서버 처리 흐름을 사용한다. 내보낸 사용자의 코드 재사용도 검증해야 한다.
5. 실제 계정으로 두 기기 로그인 → 초대 → 여행 참여 → 멤버 표시 → 저장/재시작을 검증한다.

현재 이메일 제공자 설정을 켜거나 팀 담당자의 로그인·초대 코드를 대신 재작성하지 않았다. 이번 요청은 현황과 연동 가능 여부 점검으로 수행했다.

# 최종 통합 검증

검증일: 2026-11-18. 대상: 로컬 soyul, 식당 23곳·카페 23곳 총 46곳. main은 변경하지 않는다.

## 결과

| 검사 | 결과 | 범위 |
|---|---|---|
| 전체 단위 테스트 | 97개 통과 | 진단·배분·추천·주소·검색 링크 등 |
| 앱·테스트 APK | 빌드 성공 | 기존 AGP/Gradle 버전 유지 |
| 전체 화면·실서버 | 29개 통과, 실패·오류·건너뜀 0 | 로그인·초대·계정 전환·여행 복원·진단·동행자·일정·충돌·접근 제한 |
| 두 기기 opt-in 검사 | A·B 각 1개 통과, 양쪽 cleanupErrors=[] | 독립 AVD·독립 인증 계정에서 UI와 서버 양방향 갱신 |
| 외부 링크 opt-in 검사 | 구글지도·네이버지도·블로그 각 1회 통과 | 실제 추천 버튼에서 설치된 외부 앱/브라우저 실행 |

전체 29개 검사 이후 발견한 블로그 URL 변경은 단위 97개, 실제 외부 실행 및 페이지 확인으로 검증했다. 그 뒤의 두 기기 재검사는 최종 앱 APK를 사용한다. 서로 다른 실행 묶음의 결과를 합쳐 고유 테스트 수로 표시하지 않는다.

전체 실서버 검사에서 MBTripAccountCheck/MBTripFirebaseCheck/MBTripInviteCheck/MBTripSessionCheck가 각각 통과했으며 cleanupErrors=[]를 확인했다. 기본 사용자 세션과 별개인 임시 인증·여행 자료만 생성·삭제했다.

## 독립 가상 기기 두 대

기기 A는 기존 Pixel_4a(emulator-5554), 기기 B는 같은 설치된 시스템 이미지를 사용하는 별도 MBTrip_Peer(emulator-5556)다. 같은 기기 안의 FirebaseApp 두 개를 두 기기 검사로 계산하지 않았다.

1. 양쪽에서 별도 FirebaseApp와 임시 익명 UID를 생성한다. 기본 사용자 로그인은 사용하지 않는다.
2. A는 진단 20점을 저장하고 검증용 여행을 생성하여 1회용 초대 코드를 발급한다.
3. B는 전달받은 코드로 참가하고 진단 80점을 저장한다. 서로 다른 UID의 두 멤버가 같은 여행에 보이는지 확인한다.
4. 양쪽 실제 FriendListScreen에 기기A/기기B가 존재하는지 확인한다.
5. A의 실제 TimelineScreen에서 맛집·카페 추천→본가 만두전골전문점 선택→미리보기→반영을 누른다. onBlocksChange는 실제 TravelRepository.saveBlocks를 호출한다.
6. B의 리스너·일정표에 같은 추천 장소가 나타나고 주소도 보존되는지 확인한다.
7. B가 저장소를 통해 해당 일정의 메모를 수정하면 A가 수신한다. A가 진단을 21점으로 바꾸면 B도 수신한다.
8. 각자 임시 프로필·인증을 정리하고, A는 자신이 만든 여행임을 소유자 UID와 검증 표식으로 확인한 뒤 하위 일정·멤버·초대를 정리한다.

이 검사는 실제 화면 컴포넌트를 실제 저장소에 연결하는 검증용 호스트를 사용한다. 앱 전체 내비게이션을 두 휴대전화에서 처음부터 수동으로 조작한 검사와 구분한다. B의 메모 수정·진단 저장은 저장소 호출이며 그 입력 화면을 손으로 조작한 것으로 표시하지 않는다.

첫 부팅 중 B의 System UI 응답 지연 대화상자가 관찰되어, 새 검증용 B의 해상도와 애니메이션 부하를 낮추고 재검사했다. 접근성 루트가 null을 반환하는 환경에서는 최상위 창을 dumpsys window displays로 확인한다. Android 17의 포커스 필드가 windows 출력에 없으므로 displays 출력을 사용한다. 추천 노드의 화면 표시·그리기 대기·현재 포커스를 검사한 뒤 화면을 캡처한다.

### 재실행

두 기기를 먼저 부팅하고 APK를 빌드한 뒤 PowerShell에서 실행한다.

```powershell
.\gradlew.bat assembleDebug assembleDebugAndroidTest --offline --console=plain
.\scripts\Verify-TwoDevices.ps1 -DeviceA emulator-5554 -DeviceB emulator-5556 -EvidenceDirectory "$env:TEMP\mbtrip-two-device-evidence"
```

초대 코드는 해당 실행의 임시 여행에만 쓰며 로그·handoff 파일은 커밋하지 않는다. 실행 스크립트는 양쪽 test OK와 cleanupErrors=[]를 모두 요구한다. 기본 connectedDebugAndroidTest에서는 이 검사를 건너뛰며 mbtripTwoDevice=true 및 동일 run UUID, owner/guest 역할을 두 기기에 함께 전달해야 한다.

## 지도·후기 실제 연결

| 버튼 | 실제 확인 |
|---|---|
| 구글지도 | Google Maps가 열리고 본가만두전골·입력한 시흥 동서로811번길 33 검색어가 표시됨 |
| 네이버지도 | 네이버지도 앱이 없는 환경에서 Chrome 모바일 웹으로 연결, 같은 가게명·주소 검색어와 매장 결과가 표시됨 |
| 블로그 후기 | 구형 where=blog 주소는 모바일 통합검색으로 바뀌는 문제를 재현. 실제 블로그 탭의 ssc=tab.m_blog.all로 수정 후 '네이버 블로그검색' 제목과 같은 주소·가게명 검색어를 확인 |

대표 장소의 실제 버튼 세 개를 검사했다. 46곳 각각을 모든 지도 앱 조합에서 수동 실행한 것은 아니다. 46곳 전체의 주소·출처 확인은 [주소·영업정보 검증](추천_주소_영업정보_검증.md)에 별도로 기록했다. 지도에서 보이는 실시간 평점·영업 표시는 앱 내부 저장값으로 복사하지 않는다.

브라우저/Google Maps 첫 실행 안내는 로그인 없이 진행했다. 네이버지도 설치 환경의 앱 연결과 실제 휴대전화의 권한·네트워크 변화는 후속 사용성 확인 범위다.

외부 버튼 검사 재실행 예:

```powershell
adb -s emulator-5554 shell am instrument -w -r -e class com.example.mbtrip.ExternalPlaceLinksInstrumentedTest -e mbtripExternalLinks true -e mbtripLinkTarget blog com.example.mbtrip.test/androidx.test.runner.AndroidJUnitRunner
```

mbtripLinkTarget은 google/naver/blog 중 하나다. 이 자동 검사는 외부 앱 실행을 판정하고 화면·활동 기록을 저장한다. 검색 결과의 정확성이나 당일 영업 상태까지 자동 판정하는 검사로 해석하지 않는다.

## 후속 범위

- 실제 휴대전화 2대에서 로그인부터 추천 확인까지 전체 사용 흐름과 화면 크기·네트워크 전환을 점검한다.
- 방문일 영업 상태는 매장 공지·지도에서 확인한다. 공개 자료 대조를 전화·현장 확인으로 표현하지 않는다.
- 관광·체험, 계정 전체 친구, 실시간 평점·경로 API, 다른 담당자의 숙소·교통·투표·후기 확장은 이번 마감 범위에 추가하지 않는다.
